# From Plan to Practice: Simulating Schedule Overrides

Simulation code for my Bachelor End Project (1BEPIE, Industrial Engineering, TU/e):
*From Plan to Practice: Simulating Schedule Overrides and Task Completion for Automated Personal Scheduling*.

The simulation reads a planned calendar (iCalendar `.ics`) generated by [calendar-bench](https://github.com/MaaniBeigy/calendar-bench), generates override events that depend on the persona, the context, notifications, the calendar state and the simulation parameters, updates the plan accordingly, and returns the calendar as it was actually executed. The plan and the executed calendar can then be scored with calendar-bench's own validation.

## Versions

The simulation was built in three versions. Each version leaves the earlier ones unchanged and imports their code.

| Version | Folder | Question | What it adds |
|---|---|---|---|
| **1** | [`src/`](src), [`config/`](config) | Does the override mechanism work? | Poisson arrivals, multinomial logit (postpone / skip / replace), same-day postponement, KPIs with confidence intervals, calendar-bench scoring |
| **2** | [`v2/`](v2/README.md) | How strongly do context and persona make execution deviate from the plan? | Context covariates from the `[ctx:...]` episodes, Big Five traits, concrete replacement activities, week-long replanning, a decision at every task start, health tasks from the human coach scenario, sensitivity analysis |
| **3** | [`v3/`](v3/README.md) | Which moment causes the deviation: revising the plan, starting, or finishing? | Two-stage model: a **review** of the day in advance (keep / move / drop) and **execution** at the planned time (start decision + progress: finish or stop part-way), with five execution states |

All parameters in all versions are **assumptions**, not fitted to data. Version 2 documents the source status of every parameter in [`v2/PARAMETERS.md`](v2/PARAMETERS.md).

## Input calendars

[`calendar_bench_population/`](calendar_bench_population/README.md) holds the planned calendars of all 30 persons of the calendar-bench `healthy_lifestyle_promotion` experiment: 10 per persona (`diligent_anxious_active`, `free_spirited_social_student`, `unemployed_family_caregiver`). Each person has an `.ics` file (the input of the simulation), the calendar-bench person JSON (with the sampled traits of that person) and a timeline table. The calendar used in all results so far is `diligent_anxious_active_0000`.

## Installation

Requires Python 3.9+.

```bash
pip install -r v2/requirements.txt
```

`v2/requirements.txt` (and the identical `v3/requirements.txt`) covers all three versions; the root `requirements.txt` is enough for version 1 alone. Scoring with calendar-bench needs a separate environment (see below).

## Usage

Run from the repository root. Every script takes the planned calendar as its first argument; without it, versions 2 and 3 use `default_calendar` from `v2/config/v2_config.yaml` (`data/diligent_anxious_active_0000.ics`), and version 1 uses `DEFAULT_ICS_FILE` in `src/simulation.py`. All scripts accept `--config` and `--replications`. Any calendar from `calendar_bench_population/ics/` can be passed, e.g. `calendar_bench_population/ics/free_spirited_social_student_0003.ics`.

**Version 1**

```bash
python src/simulation.py path/to/calendar.ics
```

**Version 2**

```bash
python v2/src/run_simulation.py path/to/calendar.ics
python v2/src/sensitivity.py path/to/calendar.ics --replications 10
```

**Version 3**

```bash
python v3/src/run_simulation.py path/to/calendar.ics
python v3/src/stage_ablation.py path/to/calendar.ics --replications 10
```

| Version | Output folder | Main files |
|---|---|---|
| 1 | next to the `.ics` (or `output.dir`) | `<calendar>_override_simulation.xlsx`, `<calendar>_executed_run1.ics`, `<calendar>_calendar_bench/` |
| 2 | `v2/output/` | `<calendar>_v2_simulation.xlsx`, `_sensitivity.xlsx/.csv`, `_sensitivity_tornado.png`, executed `.ics`, calendar-bench JSON |
| 3 | `v3/output/` | `<calendar>_v3_simulation.xlsx`, `_v3_stage_ablation.xlsx/.csv`, executed `.ics`, calendar-bench JSON |

Output folders are not tracked by git, except the results stored under [`results/`](results).

Comparing planning methods is not done in this repository: the plan is to run the override simulation inside calendar-bench, so each calendar-bench planner gets execution KPIs there.

### Scoring with calendar-bench

`tools/validate_with_calendar_bench.py` runs calendar-bench's own per-person validation (event constraints, LTL rules with contexts, continuity) on the plan and on the executed calendar and compares them. It works on the calendar-bench JSON folder of any version. It reads a local calendar-bench checkout and does not change it. See the [manual](MANUAL.md), section 12.

```bash
python tools/validate_with_calendar_bench.py --calendar-bench path/to/calendar-bench path/to/<calendar>_calendar_bench
```
